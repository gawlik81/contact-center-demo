**BE-142 Zakres p.2 ukonczone (2026-09-30, tylko warstwa SQL -- Zakres p.1/p.4 realizuje backend-dev-expert).** Migracja `V098__mask_audit_log_pii_on_anonymize_customer.sql`: `fn_mask_pii_jsonb_value(JSONB) RETURNS JSONB` (helper, maskuje 13 kluczy PII na "[MASKED]", klucz zostaje), `mask_audit_log_pii(p_customer_id, p_tenant_id, p_contact_ids UUID[], p_dry_run DEFAULT FALSE) RETURNS INT`, `anonymize_customer` `CREATE OR REPLACE` (sygnatura bez zmian z V096) -- nowy krok 10 woluje `mask_audit_log_pii` z JUZ zamrozonym `v_contact_ids`. Test: `backend/app/src/test/java/com/contactcenter/domain/gdpr/MaskAuditLogPiiTest.java` (8 testow, Testcontainers, fixture audit_log SEEDOWANY BEZPOSREDNIO SQL-em -- nie przez AuditAspect, bo to test warstwy SQL). `mvn clean verify -pl app`: BUILD SUCCESS, 2167 testow.

**Decyzja: WBUDOWANA w anonymize_customer, NIE osobne wywolanie z Javy.** Powod: kontakty dopasowane WYLACZNIE identyfikatorem (telefon/e-mail) zalezno od customer.phone/email, ktore anonymize_customer zeruje w ostatnim kroku -- osobne wywolanie mask_audit_log_pii z Javy PO anonymize_customer (ta sama transakcja) musialoby PONOWNIE policzyc fn_customer_subject_ids i zobaczyloby juz wyzerowane dane -> progressive narrowing (patrz [[feedback_freeze_subject_set_before_mutation]]). mask_audit_log_pii jest MIMO TO osobna, samodzielnie testowalna funkcja (przyjmuje p_contact_ids jako parametr, wiec testowalna w izolacji bez pelnego przeplywu anonimizacji) -- rozwiazuje oba postulaty ticketu (latwa testowalnosc + brak ryzyka rozjazdu z anonymize_customer) bez kompromisu. **Konsekwencja dla Javy: ZERO zmian w GdprRepository/GdprServiceImpl potrzebnych dla tej czesci** -- istniejace wywolanie `SELECT anonymize_customer(?, ?, ?, ?)::text` juz maskuje audit_log jako efekt uboczny; nowy klucz `counts.audit_log` pojawia sie automatycznie (GdprServiceImpl#toPreviewResponse iteruje generycznie po Map<String,Integer>).

**Odkrycie nieoczywiste (zweryfikowane zapytaniem na ZYWYCH danych `contact_center`, nie zgadywane): `entity_id` w `audit_log` jest BLEDNY dla WSZYSTKICH akcji `*_CREATED`, nie tylko CONTACT_CREATED.** CUSTOMER_CREATED: 1/1 wiersz live ma `entity_id = tenantId` (0/1 ma `entity_id = customerId`). CONTACT_CREATED: 263/263 ma `entity_id = tenantId` (0/263 ma `entity_id = contactId`). CUSTOMER_UPDATED (7/7) i CONTACT_ABANDONED/ACCEPTED/AGENT_ASSIGNED/DISPOSITION_SET (14+28+363+400) maja `entity_id` POPRAWNY we wszystkich wierszach -- tylko `*_CREATED` jest bledny, prawdopodobnie wspolny blad w `AuditAspect` (encja nie ma jeszcze przypisanego/odczytanego ID w momencie CREATED). Poleganie wylacznie na `entity_id` (jak dosłownie sugerowal tekst tickietu BE-142) pomineloby WSZYSTKIE wiersze `*_CREATED` podmiotu -- dlatego dopasowanie w `mask_audit_log_pii` jest oparte GLOWNIE na tresci JSON (`new_value`/`old_value ->> 'customerId'/'contactId'`), z `entity_id` jako dodatkowa, tansza sciezka. Zapisane w TASKS-BACKEND.md BE-142 jako sugestia naprawy dla backend-dev-expert (Zakres p.1, poza zakresem SQL).

**RLS UPDATE na audit_log pod app_user -- zweryfikowane DZIALANIEM (nie analogia), nowe wobec DB-062:** `UPDATE audit_log SET new_value = new_value WHERE tenant_id = ...` pod `SET LOCAL ROLE app_user` (transakcja z ROLLBACK, scratch dane zywej bazy) daje `UPDATE 0` -- CICHO, bez bledu. DB-062/V096 juz udokumentowalo to dla `contact`/`email_message`/`social_message` (brak polityki UPDATE = cicho 0) i dla `INSERT INTO audit_log` (twardy blad, brak polityki INSERT) -- ale NIE bylo wprost zweryfikowane dla UPDATE na SAMEJ audit_log, co ten ticket wymagal sprawdzic dzialaniem. Konsekwencja: bez regresji, bo `anonymize_customer` pod `app_user` w trybie rzeczywistym i tak juz konczy sie twardym bledem na koncowym `INSERT INTO audit_log` (V096) i cofa cala transakcje -- nowy krok mask_audit_log_pii jest "ukryty" za tym istniejacym ograniczeniem.

**RECORDING_URL_REQUESTED (entity_type=CONTACT) POZA ZAKRESEM BE-142 -- zweryfikowane bez potrzeby jawnego wykluczenia po `action`:** JSON tej akcji NIE ma klucza `contactId` (klucze: fileName/expiresAt/contentType/presignedUrl/durationSeconds), a jej `entity_id` nie pasuje do zadnego kontaktu podmiotu (0/100 na danych live -- prawdopodobnie ID samego nagrania/zadania, nie kontaktu). Dopasowanie JSON-owe (`? 'contactId'`) naturalnie wyklucza te wiersze bez dodatkowego filtra `action NOT IN (...)`.

**Wzorzec (przyszle rozszerzenia audit_log/GDPR):** gdy nowa funkcja SQL mutuje dane na podstawie zbioru wyznaczonego przez `fn_customer_subject_ids`, a inna czesc TEJ SAMEJ operacji (anonymize_customer) juz zeruje kolumny, od ktorych ten zbior zalezy -- NIE wywolywac `fn_customer_subject_ids` ponownie w osobnym kroku/wywolaniu, tylko PRZYJMOWAC gotowy, zamrozony zbior jako parametr (UUID[]). To pozwala funkcji byc JEDNOCZESNIE: (a) osobna i testowalna w izolacji, (b) bezpieczna wobec progressive narrowing, bez kompromisu miedzy tymi cechami.
