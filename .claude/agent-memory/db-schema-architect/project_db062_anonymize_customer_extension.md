**DB-062 ukończone (2026-09-24).** Migracja `V096__extend_anonymize_customer_gdpr_art17.sql`: `DROP FUNCTION anonymize_customer(UUID,UUID,UUID)` (stara VOID) + `CREATE FUNCTION anonymize_customer(p_customer_id, p_tenant_id, p_user_id, p_dry_run DEFAULT FALSE) RETURNS JSONB`. Test: `backend/app/src/test/java/com/contactcenter/domain/gdpr/AnonymizeCustomerExtensionTest.java` (13 testów, Testcontainers, jedna baza + bogaty fixture w `@BeforeAll`). Naprawiono `ContactRefIntegrityNarrowingTest#anonymizeCustomer_worksForCustomerWithContacts` (nowa sygnatura/typ zwracany).

**Why:** rozszerzenie zakresu anonimizacji na `scheduled_callback`, `campaign_contact`/`_archive`, `contact.notes`/`recording_url`, transkrypcje/podsumowania AI, `email_message.cc/bcc`, `customer.external_id`/`gdpr_consent`/`custom_fields`, `contacts_dw` — reużywa `fn_customer_subject_ids` z [[project_db061_export_customer_data_subject_helper]] (D9 = A) bez modyfikacji.

**Kontrakt JSONB:** `{dry_run, counts: {customer, contact, scheduled_callback, campaign_contact, campaign_contact_archive, contact_transcription, contact_ai_summary, email_message, social_message, contacts_dw}, matched_by_link, matched_by_identifier, s3_keys}`. `counts.customer` ZAWSZE `1` przy sukcesie (customer jest bezwarunkowo dosanityzowywany — brak filtra „już zanonimizowany”, żeby dociągnąć `custom_fields`/`gdpr_consent`/`external_id` nawet u klienta zanonimizowanego dawniej tylko ścieżką Javy). Wszystkie POZOSTAŁE liczniki mają w `WHERE` dodatkowy warunek „jeszcze jest co zanonimizować” (literal `'ANONYMIZED'`/pusta wartość/status operacyjny) — zbiegają do zera przy powtórnym wywołaniu (idempotencja). `matched_by_link`/`matched_by_identifier` to ROZMIAR zbioru podmiotu (nie delta) — identyczna definicja jak w `export_customer_data`, celowo, dla testu spójności między podglądem DB-062 a eksportem DB-061.

**How to apply:** przy przyszłych zmianach `anonymize_customer` (BE-129 integracja, ewentualne DB-063+ rozszerzenia) — zachowaj wzorzec „zamroź zbiór podmiotu RAZ na starcie” (patrz [[feedback_freeze_subject_set_before_mutation]]) i pamiętaj że `audit_log` blokuje pełne wywołanie pod `app_user` (patrz [[feedback_rls_insert_vs_update_semantics]]).

**Decyzja o kolizji `record_id` (DB061-08, z code review DB-061):** wariant (a) rozszerzony o twardy guard — `RAISE EXCEPTION` PRZED jakąkolwiek mutacją, gdy w zbiorze podmiotu dla `campaign_contact`/`campaign_contact_archive` istnieje `record_id` współdzielony przez ≥ 2 różne `campaign_id` w tym samym tenancie. Praktycznie martwy kod (kolizja `uuid_generate_v4()` kryptograficznie nieprawdopodobna), ale zamienia potencjalne ciche uszkodzenie danych cudzej kampanii w bezpieczny, głośny błąd. Test: jawny `INSERT` z tym samym UUID `record_id` w 2 kampaniach tego samego tenanta.

**Reguła mostu w praktyce (nie tylko w `fn_customer_subject_ids`):** kontakt dopasowany WYŁĄCZNIE przez `identifier` (telefon/e-mail klienta, `customer_id IS NULL`), niosący `campaign_contact_record_id` → odpowiadający rekord kampanii I callback (dopięty tym samym `campaign_contact_record_id`) są FAKTYCZNIE anonimizowane przez `anonymize_customer` (nie tylko wykazane w `fn_customer_subject_ids`), mimo że same mają INNY telefon i `customer_id = NULL`. UPDATE-y w V096 działają poprawnie automatycznie, bo tylko joinują wynik `fn_customer_subject_ids` po `entity_id` — cała logika mostu żyje wyłącznie w tej jednej funkcji pomocniczej (DRY, reużyta bez zmian).

**contacts_dw guard:** `IF EXISTS(...information_schema.columns...) THEN UPDATE contacts_dw ... END IF` — PL/pgSQL planuje statyczne SQL LENIWIE (dopiero gdy dana gałąź IF jest faktycznie wykonana), więc gdy DB-078 usunie kolumnę `remote_address`, ta gałąź po prostu nigdy się nie wykona i funkcja nie pęknie — NIE trzeba dynamicznego `EXECUTE`/`format()`. Potwierdzone testem: `ALTER TABLE contacts_dw DROP COLUMN remote_address` wewnątrz tej samej cofanej transakcji testowej, funkcja dalej działa (DDL jest transakcyjny w Postgresie, więc to bezpieczne do testowania bez osobnej bazy).
