Numer nowej migracji wybieraj po TRZECH źródłach, nie po samym `ls backend/src/main/resources/db/migration/`:
1. katalog na bieżącej gałęzi,
2. `SELECT version, description FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 5` na żywej bazie (`docker exec cc-postgres psql -U ccapp -d contact_center`),
3. `git ls-tree -r --name-only <branch> -- backend/src/main/resources/db/migration` dla KAŻDEJ gałęzi z `git branch -a` (lokalne gałęzie feature bywają niepushowane).

**Why:** Sesja DB-055 (2026-09-19): zlecenie mówiło "V092 jest wolne (V091 najwyższe na develop)", a w rzeczywistości V092 (`social_integration_global_unique_page`) było już ZASTOSOWANE w żywej bazie (2026-08-29) i istniało na lokalnej gałęzi `feature-socialmedia` (niepushowanej). Użycie V092 dałoby duplikat wersji po merge i niezgodność checksum na żywej bazie.

**How to apply:** Gdy najwyższy numer w bazie/innej gałęzi jest wyższy niż na `develop`, weź następny wolny (tu V093) i ZGŁOŚ właścicielowi pułapkę wdrożeniową: build z samego `develop` (V091 + V093 bez pliku V092) na bazie z zastosowanym V092 nie przejdzie walidacji Flyway (`V092 MISSING_SUCCESS`, "Detected applied migration not resolved locally: 092") — V092 przestaje być `*:future` (domyślnie ignorowane), gdy lokalnie rozpoznane jest wyższe V093. Najpierw trzeba wprowadzić plik V092 na develop (merge gałęzi), potem wdrażać nową migrację. Zweryfikowane Flyway API (10.20.1) na kopii `flyway_schema_history`. Uwaga: `backend/app/target/classes/db/migration` może zawierać NIEAKTUALNE pliki z wcześniejszych buildów innych gałęzi (maven nie czyści) — `mvn verify` bez `clean` może więc testować łańcuch z cudzym V092; wariant "czysty develop" sprawdzaj osobno (Flyway API na `filesystem:` z kopią katalogu migracji).

**Druga instancja tej samej pułapki (DB-064/V099, 2026-10-01):** żywa baza dev (`cc-postgres`) miała już zastosowane V098 (`mask_audit_log_pii_on_anonymize_customer`) z NIEZMERGOWANEJ gałęzi `feature/epic-30-be142-fe112`, podczas gdy gałąź robocza `feature/epic-30-social-message-partitioning` miała katalog migracji kończący się na V097 (V098 nie istniał tam jako plik). Wybrano V099 jako kolejny wolny (poprawnie — zero kolizji na żadnej lokalnej gałęzi/żywej bazie dla V099). Próba realnego `flyway.migrate()` przez `RunFlyway.java` na `cc-postgres` z katalogu migracji TEJ gałęzi zakończyła się identycznym `MISSING_SUCCESS` dla V098. **Decyzja:** NIE kopiować tymczasowo pliku V098 z sąsiedniej gałęzi do katalogu migracji tylko po to, żeby wymusić aplikację na współdzielonej żywej bazie dev — zbyt ryzykowne (inne agenty/procesy mogą korzystać z tego samego kontenera równolegle, a plik nigdy nie trafia do gita tej gałęzi więc nie daje realnego dowodu zgodności z CI). Zamiast tego: (1) dry-run SQL w transakcji z jawnym `ROLLBACK` na `cc-postgres` (potwierdza składnię i efekt `DO $$...RAISE EXCEPTION` bloku weryfikacyjnego), (2) pełny dowód przez Testcontainers (świeży kontener, `Flyway.configure().locations("classpath:db/migration")` — świeża baza nie ma wcześniej zastosowanego niczego, więc "dziura" numeracji V097→V099 jest całkowicie nieszkodliwa, Flyway tylko wymaga rosnącej kolejności, nie kolejnych liczb całkowitych). Żywa baza dev pozostała nietknięta (zweryfikowano `flyway_schema_history`/`pg_class` przed i po sesją — identyczne). Zasada ogólna: gdy współdzielona baza dev ma zastosowaną migrację z niezmergowanej gałęzi, której plik nie istnieje na Twojej gałęzi, NIE wymuszaj live-apply przez tymczasowe kopiowanie cudzego pliku — Testcontainers (świeży kontener per uruchomienie testu) jest odporny na tę lukę i jest wystarczającym dowodem, a próba "naprawy" żywej bazy to praca poza zakresem Twojego ticketu i ryzyko dla innych równoległych sesji.
