---
name: project_global_exception_handler_response_status_bug
description: GlobalExceptionHandler's catch-all Exception.class handler swallows raw ResponseStatusException and returns 500 instead of the declared status code, in the full Spring MVC resolver chain (verified empirically with MockMvc standaloneSetup).
type: project
---

`com.contactcenter.api.GlobalExceptionHandler` (`backend/app/src/main/java/com/contactcenter/api/GlobalExceptionHandler.java`) has a catch-all `@ExceptionHandler(Exception.class)` (`handleGenericException`) but no dedicated `@ExceptionHandler(ResponseStatusException.class)` and does not extend `ResponseEntityExceptionHandler`. Several existing service classes throw raw `org.springframework.web.server.ResponseStatusException` directly (e.g. `SocialIntegrationServiceImpl.getDecryptedIntegration()` → 404/422, `loadIntegrationForDelete()` → 404, several `SocialOAuthController` 400s) expecting Spring to honor the status code passed to the constructor.

**Why this matters:** verified empirically (2026-08-29, `MockMvcBuilders.standaloneSetup(...).setControllerAdvice(new GlobalExceptionHandler())`) that a `ResponseStatusException(HttpStatus.CONFLICT, ...)` thrown from a controller gets intercepted by `ExceptionHandlerExceptionResolver` and matched against the broad `@ExceptionHandler(Exception.class)` handler (since there's no more-specific match registered), which unconditionally returns **HTTP 500**, silently discarding the intended status code. This is NOT visible from the existing unit tests for `SocialIntegrationServiceImpl`/`WhatsAppAdapter`, because those tests call the service method directly with Mockito and assert on the thrown `ResponseStatusException`'s `getStatusCode()` — they never exercise the real MVC exception-resolution chain, so they pass despite the bug.

By contrast, exceptions with a **dedicated** `@ExceptionHandler` in `GlobalExceptionHandler` (e.g. `ConflictException` → `handleConflictException` → 409, `ResourceNotFoundException` → 404, `TwilioApiException`/`WhatsAppApiException` → 502) resolve correctly, confirmed with the same empirical test.

**How to apply:** when adding new error paths in this codebase that must reach the client with a specific HTTP status, prefer throwing (or adding) one of the existing dedicated domain exceptions mapped in `GlobalExceptionHandler` (`ConflictException`, `ResourceNotFoundException`, `InvalidOperationException`, etc.) rather than a raw `ResponseStatusException`, unless/until this systemic bug is fixed (e.g. by adding a proper `@ExceptionHandler(ErrorResponseException.class)`/`ResponseStatusException.class` handler, or making the generic handler more selective). This is a repo-wide latent bug beyond any single feature — worth flagging as a separate fix ticket, not something to silently work around forever.
