**DB062-01 (prior blocker) confirmed closed, two layers deep:** V096 now has `IF p_dry_run IS NULL THEN RAISE EXCEPTION` as the first statement (SQL-side fix, already reviewed in DB-062). Independently re-verified for BE-129: the entire Java call chain (`GdprController` → `GdprServiceImpl.anonymizeCustomer`/`previewAnonymizeCustomer` — literal `false`/`true`, never a field — → `GdprRepository.anonymize(..., boolean dryRun)` — primitive, never boxed `Boolean` — → `.setParameter("dryRun", dryRun)`) cannot reintroduce this bug class even if the SQL-side guard were ever removed. Don't re-flag.

**New findings, this ticket:**
- **BE129-01 (major, confirmed by code/lock-tracing, not by executing a concurrency test):** the "in-progress record" guard (`GdprRepository#hasInProgressRecords`, plain `SELECT`, no `FOR UPDATE`) and the actual `anonymize_customer` mutation run as two separate statements inside one `@Transactional` method. Under READ COMMITTED (Postgres default, no isolation override here), a row that transitions `campaign_contact.status` → `DIALING` (via `ProgressiveDialerServiceImpl`'s `SELECT ... FOR UPDATE SKIP LOCKED` + `UPDATE`, `ProgressiveDialerServiceImpl.java:406-459`) *after* the guard's SELECT but *before* `anonymize_customer`'s own `UPDATE campaign_contact` (V096, unconditionally zeroes phone/name/email regardless of status — only the `status` column itself is conditionally touched) will not be caught, and the mutation zeroes PII on a record that is now genuinely mid-call. Same pattern for `scheduled_callback`/`PROCESSING` via `ScheduledCallbackRepository#updateStatusIfPending` (plain conditional `UPDATE ... WHERE status='PENDING'`). Fix: add `FOR UPDATE` (no `SKIP LOCKED`) on the guard's subject rows — this makes the dialer's `SKIP LOCKED` claim politely skip the row (non-blocking), and makes the callback executor's plain `UPDATE` wait and then correctly no-op once it sees the post-anonymize state. See pattern #14 in [[project_recurring_antipatterns]].
- **BE129-02 (major, test-coverage gap, confirmed by repo-wide grep):** zero tests anywhere (before or after this diff) exercise `GdprController` via MockMvc/Spring — no proof `@PreAuthorize("hasAnyRole('ADMIN','SUPERVISOR')")` actually blocks e.g. AGENT for any of its three endpoints (including the brand-new `GET .../anonymize/preview`), and `GlobalExceptionHandlerTest.java` (untouched by this diff) has no test at all for `ConflictException`/`handleConflictException` — so the new 409 contract is proven only at the "Java exception propagates out of a plain `@InjectMocks` controller method call" level, never at the "Spring actually returns HTTP 409 with a `ProblemDetail` body" level. Some sibling controllers in this repo (`EmailAttachmentControllerTest`, `RetentionControllerTest`, `CustomerImportControllerTest`) DO use `MockMvc`/`@WithMockUser` — this isn't a universal repo convention gap, `GdprController`/`CustomerController` are just missing it. Recommend a `GdprControllerTest` before wide rollout.
- **BE129-03 (minor, confirmed by code-reading):** `GdprRepository#anonymize`/`#exportCustomerData` call `assertSameTenant(tenantId, customerId)` where `tenantId` is the exact same value the caller just read from `TenantContext.getTenantId()` moments earlier in the same synchronous thread — the check compares the context to itself and can never throw in practice. Not a security hole (the real tenant filter is the `WHERE tenant_id = p_tenant_id` predicates, already verified sound in DB-061/DB-062), but it's a misapplication of the project's `assertSameTenant(entity.getTenantId())` convention (which assumes an *independently*-sourced entity tenant_id, e.g. fetched from DB) and could give a false sense of protection to a future reader. Worth watching for in other new repositories that wrap raw/native SQL calls without an actual JPA entity to compare against.

**Confirmed sound, don't re-litigate:** DELETE/POST consolidation is real (byte-level diff shows `CustomerController#anonymizeCustomer` now calls `gdprService.anonymizeCustomer(id)` directly, zero duplicated validation/audit logic); exactly one audit entry per operation (grep confirms `GdprServiceImpl` never calls `auditLogService` for anonymize, and `@Audited(CUSTOMER_ANONYMIZED)` was removed from the now-dead `CustomerServiceImpl.anonymizeCustomer`); DB→S3 ordering is correct because zero `@Transactional` annotations exist anywhere in `GdprServiceImpl.java` (only `GdprRepository#anonymize` is transactional, a separate Spring bean, so its proxy commits before control returns to the caller — no self-invocation trap); S3 per-key failures don't abort the cleanup loop (proven both by reading `cleanupS3Objects` and by `GdprServiceIntegrationTest#s3FailureAfterCommit_...` on a real DB); the two S3 key allow-lists (`EmailAttachmentKeys.isOwnedByTenant` vs `isRecordingKeyOwnedByTenant`) are structurally disjoint (different literal roots, `tenantId` is always a UUID so can never collide with the literal `"email-attachments"` prefix) and a key matching neither is logged + counted as a failure, not silently dropped; the three deprecated `CustomerService(Impl)/CustomerRepository#anonymize*` methods have zero remaining callers anywhere in `backend/` outside each other (confirmed by grep) — `@Deprecated`-not-removed is a safe, justified choice; guard SQL's column/status literals (`campaign_contact.status='DIALING'`, `scheduled_callback.status='PROCESSING'`, `record_id`/`callback_id` as `entity_id`) were independently verified against the actual producers (`ProgressiveDialerServiceImpl`, `ScheduledCallbackExecutor`, V095's `fn_customer_subject_ids`), not just trusted from the ticket text — zero drift found.

**Minor/nit test-quality items (not blocking):** `GdprServiceIntegrationTest`'s DB061-08 collision test asserts only `isInstanceOf(RuntimeException.class)` (too broad — wouldn't distinguish the real guard from an unrelated bug); S3 cleanup failures are logged (ERROR) but never persisted anywhere durable/queryable (satisfies the letter of the AC, which explicitly allows "log", but is operationally fragile for an irreversible PII operation); `fn_customer_subject_ids` is computed twice per real anonymize call (once in the Java guard, once inside `anonymize_customer`) — same accepted large-customer performance risk as DB-061/DB-062, not new.

**Verification method used:** traced the `dryRun` parameter type end-to-end from controller to JDBC bind (not just at the repository boundary) to confirm no boxed `Boolean`/nullable-DTO regression of DB062-01; read V096's actual `UPDATE campaign_contact` predicate (not just the ticket's prose) to confirm the guard's race window has a real, non-cosmetic consequence (PII zeroed regardless of status); grepped the real claimer code (`ProgressiveDialerServiceImpl`, `ScheduledCallbackRepository`) for its locking primitive before asserting a race exists, rather than reasoning about it abstractly; grepped the whole test tree for `GdprController`/`ConflictException` before claiming a test gap, rather than assuming from absence in the diff alone.
