Reviewed 2026-09-24 (CR-DATABASE.md "Review: V095…fix_export_customer_data_and_add_subject_helper.sql (DB-061)") = 4/5, "zatwierdzić z poprawkami". Zero blockers/majors. Full details in CR-DATABASE.md; key points to remember for [[project_epic30_purge_contract_open_items]] and for reviewing DB-062:

**Confirmed sound (don't re-litigate):** two-stage (non-recursive) CONTACT-then-derived resolution is the right shape for this schema (graph depth is exactly 2, verified against every migration that adds a cross-entity column). No JOIN-based fan-out anywhere in `fn_customer_subject_ids` — every sub-CTE filters its own source table with a flat `WHERE ... OR ...`, so duplicate-row risk for a dual-matched entity (e.g. contact matched by both `customer_id` AND `remote_address`) is structurally impossible, not just untested. `link` beats `identifier` when both match (CASE order), confirmed by fixture (`CONTACT_LINKED`) and by hand-verifying the `matched_by_link`/`matched_by_identifier` totals (9/4) against the full fixture — exact match, strong independent proof the JOIN/CASE logic is correct. Every subquery in both functions (17 total) has an explicit `tenant_id = p_tenant_id` filter, including `campaign_contact`/`campaign_contact_archive` which have **no RLS policy at all** (verified via grep — V009/V015 never add `CREATE POLICY`/`ENABLE ROW LEVEL SECURITY` for these two tables) — this is the one place a missing filter would be a real cross-tenant leak, and it's present everywhere it's read. `GdprServiceImpl#exportCustomerData` really does write `GDPR_EXPORT` to audit_log (`GdprServiceImpl.java:61-72`) — confirmed in code, not trusted from the note — so dropping the SQL-side `INSERT INTO audit_log` doesn't create an audit gap. Independent grep confirms zero other callers of `export_customer_data` anywhere in the repo besides the new test — the `CREATE OR REPLACE` (same signature) is safe.

**Known limitation, deliberately accepted (don't re-flag):** `fn_normalize_phone` strips everything except digits/`+` — false negative for numbers missing the `+48` country code, explicitly documented. `SOCIAL_MESSAGE` only ever gets `matched_by='link'` (no identifier fallback — `sender_external_id` is a platform ID, not a phone/email) — deliberate, documented in the function's `COMMENT`.

**Open items carried into DB-062 review (all minor/nit, none blocking DB-061's merge):**
- **DB061-01 (minor, doc-only):** migration header + TASKS-DATABASE.md note claim `scheduled_callback` has `FORCE ROW LEVEL SECURITY` — false (grepped every migration touching the table: V032/V037/V038/V047/V054, only `ENABLE`, never `FORCE`). Harmless in practice (`app_user` isn't the table owner, so `FORCE` doesn't matter for it), but DB-062's own RLS write-path AC (R1) will describe `scheduled_callback` too — check it doesn't repeat the same false "(FORCE)" claim.
- **DB061-02 (minor, test-quality):** the "no duplicate row" assertions for `contacts`/`scheduled_callbacks`/`campaign_records` in `ExportCustomerDataSubjectHelperTest` convert the JSON array to a `Set` before comparing (`idsOf()` helper) — this **cannot** catch a future duplicate-row regression, unlike the `hasSize(n)` assertions correctly used for `email_messages`/`social_messages`/etc. in the same file. If DB-062 writes similar array-shaped assertions (e.g. for its dry-run preview), use `hasSize` + id-set, not id-set alone.
- **DB061-03 (minor, test-coverage gap):** the "bridge rule" (`contact.campaign_contact_record_id` propagating to `campaign_contact`/`scheduled_callback`) is only tested via a contact that ALSO has `customer_id` set directly (so it's really a "link contact + bridge" test, not the harder "identifier-only contact + bridge" case the DB-061 note calls representative). Code inspection shows the SQL doesn't special-case this (the bridge CTE joins all of `subject_contacts` regardless of `matched_by`), so it's very likely fine — but DB-062 should add the missing fixture combination (contact with `customer_id=NULL` + phone-identifier match + `campaign_contact_record_id` set) since DB-062 reuses the exact same helper function.
- **DB061-04 (minor, test-coverage gap):** no test calls `export_customer_data`/`fn_customer_subject_ids` for a customer with **zero** associations (fully empty subject) — the fixture already has a ready candidate (`CUSTOMER_OTHER_SAME_TENANT`, phone=[]/email=[], used only as a negative-control owner, never as the export subject itself). Cheap to add; DB-062's own dry-run test suite should cover this if DB-061 doesn't get amended first.
- **DB061-05/06/07 (nit):** `COMMENT ON FUNCTION fn_customer_subject_ids` doesn't explicitly state the link-wins-over-identifier tie-break (only inferable from `CASE` order) — worth one sentence, since DB-062's `p_dry_run` surfaces `matched_by` to operators (FE-112). `att->>'s3_key'` extraction doesn't guard against non-string JSON values (unlike the more defensive `EmailAttachmentKeys.extractS3Keys` in Java) — currently unreachable given writers always emit strings, pure defensive nit. `fn_customer_subject_ids` itself is never tested directly (only transitively through `export_customer_data`'s JSON) — recommend DB-062 add a direct `SELECT * FROM fn_customer_subject_ids(...)` test as its first step, since it's the shared contract both tickets depend on.
- **DB061-08 (nit, design assumption):** `campaign_contact`/`campaign_contact_archive` PK is composite `(record_id, campaign_id)`, but `entity_id` in the helper's output carries only `record_id` (safe today only because `record_id` is always `uuid_generate_v4()`-generated, never user-supplied). If DB-062 uses these `entity_id` values to scope `UPDATE`/`DELETE`, it must use the full composite key from the actual fetched row, not assume `record_id` alone pins one row.

**Verification method that worked (reuse for DB-062):** don't trust migration/task-note claims about schema — independently grep the actual `CREATE TABLE`/`ALTER TABLE` migrations for every column referenced (caught the RLS-FORCE inaccuracy this way). Hand-compute expected `matched_by_link`/`matched_by_identifier` totals from the test fixture and compare to the asserted numbers — cheap, and a strong independent correctness signal beyond "the test passes". Check whether array-based JSON assertions use `hasSize` vs a `Set`-collapsing helper before trusting a "no duplicates" test. One read-only live-DB query (`flyway_schema_history` ORDER BY installed_rank DESC LIMIT 5, no function calls) is enough to confirm a new migration is unapplied — no need to touch the DB further to validate the "not applied to live DB" constraint.
