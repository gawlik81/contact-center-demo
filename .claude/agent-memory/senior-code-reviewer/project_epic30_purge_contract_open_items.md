NOT via the "progress > 0" guard originally specified in BE-124 — that guard was deliberately dropped, see new open item below (BE126-01).

**Closed by BE-143 (2026-09-22) — do not re-flag:**
- Unticketed send-path s3Key hole (DESIGN U18, `EmailSendServiceImpl#buildAttachmentPart`): fixed via `validateAttachmentKeys` as literal step 0 of `sendReply`/`sendNew`, before any DB/S3/SMTP I/O — verified in code AND via `verifyNoInteractions` unit tests. `EmailAttachmentController#downloadAttachment`'s bare `startsWith` (no `..` rejection) also fixed, now delegates to the same `isOwnedByTenant`.

**Still open / deferred — carry to BE-127, BE-129, BE-131, and to BE-126 pt (b) when picked up:**
- **BE126-01 (new, latent major)**: the H-1 fix removed the "progress==0 stops the whole purge" safety net from BE-124 for `contact` DELETEs specifically (not just social). `deleteContacts`'s cursor always advances a full page; the WARN log only fires when the *entire* page returns 0 deletes, not on a partial silent shortfall. If `contact` ever gets a DELETE-restricting RLS policy while the app role loses `BYPASSRLS` (today: `ccapp` is superuser+BYPASSRLS, confirmed live — no impact now), some contacts could be silently un-purgeable forever with zero log signal, even though their messages were already deleted. Not a regression to fix now; needs a doc comment + widening the WARN condition to `actuallyDeletedContacts.size() < deletableIds.size()`.
- `deleteContacts` (`ContactRepository`) drops the already-known `started_at`/`cutoff` before the DELETE, so (confirmed via `EXPLAIN`) it scans all partitions — same cost profile as the pre-existing `deleteBatchOlderThan`, NOT a regression, but a cheap missed optimization (adding `AND started_at < :cutoff` would let the planner prune like `findContactIdsOlderThan` already does).
- Social (`SocialMessageService#purgeByContactIds` returns only `int`, no `contactIdsBlocked`) remains explicitly out of scope of BE-126, same latent risk as before (DB-064 before DB-074 ordering still needed).
- `EmailAttachmentStorageService#delete(String)` still has no built-in tenant guard (BE125-04) — BE-143 deliberately chose to add allow-list methods on `EmailAttachmentKeys` instead of changing this signature; any future caller (BE-126 pt (b), BE-129, BE-131) must call `isOwnedByTenant`/`isRecordingKeyOwnedByTenant` themselves before invoking `delete`.
- `PurgeResultDto.errorMessage` Javadoc (`domain/retention/dto/PurgeResultDto.java:28`) still says "at status=FAILED only" — stale since BE-126 legitimately populates it for COMPLETED-with-S3-warning too. One-line fix, not yet done as of 2026-09-22.
- Process gap (both BE-126 and BE-143 tickets note this about each other): the "contractual note" cross-referencing the BE-143 API decision was never back-filled into BE-126/BE-129/BE-131's TASKS-BACKEND.md sections (executors could only edit their own ticket's section per-iteration). Check for this when those tickets are picked up — the decision itself (`isRecordingKeyOwnedByTenant`) is sound, just not cross-linked in the doc.

**Also carry to BE-129 (from DB-062 review, 2026-09-24, see [[project_db062_anonymize_customer_extension_review]]):** `anonymize_customer`'s `p_dry_run` parameter has a proven (execution, not just static) blocker — explicit SQL `NULL` silently takes the destructive real-anonymization path instead of erroring or previewing, because `DEFAULT FALSE` only protects an omitted argument, not an explicit NULL. Verify this was fixed (new migration or unshipped V096 edit) before BE-129 wires up any caller, and verify the Java-side DTO/service uses a primitive `boolean` (not boxed `Boolean`) as defense in depth. Also: all `anonymize_customer` exceptions collapse to SQLSTATE `P0001` (single top-level `EXCEPTION WHEN OTHERS`, inherited from V013) — BE-129 can only distinguish the DB061-08 collision guard from a generic failure by substring-matching `"DB061-08"` in the message text, not by SQLSTATE.
