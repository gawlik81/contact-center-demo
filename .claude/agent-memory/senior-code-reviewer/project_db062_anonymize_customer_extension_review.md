Reviewed 2026-09-24 (`CR-DATABASE.md` "Review: V096…extend_anonymize_customer_gdpr_art17.sql (DB-062)") = **2/5, "WYMAGA ZMIAN"** — one blocker, proven by execution, not just static reading. Full details in CR-DATABASE.md; key points for [[project_epic30_purge_contract_open_items]] and for reviewing BE-129 (the only planned future caller of `anonymize_customer`).

**The blocker (DB062-01), and why it matters beyond this one function:** `anonymize_customer(p_customer_id, p_tenant_id, p_user_id, p_dry_run BOOLEAN DEFAULT FALSE)` — a PL/pgSQL `DEFAULT` clause only protects an **omitted** argument. It does NOT protect an **explicitly passed SQL NULL** for that same parameter. `IF p_dry_run THEN ... END IF` treats a NULL condition as false (standard PL/pgSQL semantics: NULL in a boolean IF falls through, doesn't error). So a caller that explicitly binds NULL for the 4th arg (e.g. a boxed `Boolean dryRun` that's null via JDBC `ps.setObject`, or a JSON DTO field that's absent and deserializes to `null` rather than being omitted from the call) silently takes the **destructive real-anonymization path**, not a safe preview — and the JSONB result even claims `"dry_run": false`, giving zero signal anything unusual happened.

**Proven empirically, not just reasoned:** built a scratch DB (`scratch_db062_review`, full V001..V096 chain replayed via `psql -f` in order — zero errors, independent confirmation the migration chain applies cleanly), seeded a minimal customer+contact, called `SELECT anonymize_customer(cust, tenant, NULL::uuid, NULL::boolean)` inside a `ROLLBACK`-ed transaction. Result: `remote_address` went from a real value to `NULL`, `customer.is_deleted` flipped `f`→`t`, `"dry_run": false` in the JSONB. Contrast: the 3-arg (omitted) call correctly used `DEFAULT FALSE` and also mutated — i.e. "omitted" and "explicit NULL" behave *identically* today, which is the bug (they should not: NULL should fail loud, not silently mean "destroy").

**Recommended fix (cheap, same philosophy the author already used for the DB061-08 guard):** add `IF p_dry_run IS NULL THEN RAISE EXCEPTION '...'; END IF;` as literally the first statement after `BEGIN`. Turn silent destruction into a loud, safe error — don't guess at caller intent for an irreversible GDPR operation.

**Generalizable lesson (added to [[project_recurring_antipatterns]] as pattern #13):** any PL/pgSQL (or any language with default-parameter semantics separate from NULL-handling) function that uses a `BOOLEAN ... DEFAULT FALSE`-style parameter as a **safety/preview switch for an irreversible operation** must explicitly reject NULL, not rely on `DEFAULT` — `DEFAULT` and "caller passed NULL" are different code paths and only one of them is protected. Check this pattern proactively in any future review of destructive/irreversible SQL functions in this codebase (retention purge functions, any future `anonymize_*`/`purge_*`/`delete_*` with a dry-run flag).

**Carry to BE-129 review:** when BE-129 (the Java caller wiring up `anonymize_customer`) is reviewed, verify (a) DB062-01 was actually fixed in a new migration (V097+, not a V096 edit — V096 must not be edited once applied per project Flyway rules) or the fix landed in V096 itself if it hadn't shipped anywhere yet, (b) the Java DTO/service layer for the dry-run flag uses a primitive `boolean` (not boxed `Boolean`) or otherwise structurally cannot pass null through to the JDBC binding, as defense in depth even after the SQL-side fix, (c) error handling for the DB061-08 collision guard — all exceptions from this function collapse to SQLSTATE `P0001` (generic `raise_exception`, wraps `SQLERRM`) since the whole function body is one `EXCEPTION WHEN OTHERS` block (inherited from V013) — BE-129 can only distinguish "guard fired, needs manual intervention" from "generic failure" via substring-matching `"DB061-08"` in the (Polish-language) error message text, not via SQLSTATE.

**Verification method that worked well here, reuse for future irreversible-SQL-function reviews:** don't just reason about language semantics (NULL-vs-DEFAULT) — build a throwaway scratch DB (`pg_dump -s` of live schema, or full migration replay via `psql -f` in numeric order) and *execute* the suspected edge case inside a `ROLLBACK`-ed transaction. This is explicitly permitted by this project's review constraints (never touch the live DB with the function under test, but a scratch DB is fair game) and turns a "plausible bug" into "proven bug with an exact before/after diff" — much stronger for a blocker-severity finding on an irreversible-data function.
