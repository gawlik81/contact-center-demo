Analiza "kolejne tabele do partycjonowania" wykonana 2026-09-20 (baza V093, PG 16.13, bez zmian w bazie/repo). Wnioski (zmierzone, nie założenia):

- **Realni kandydaci są tylko dwaj: `email_message` i `social_message`** (tabele treści, PII, rosną z liczbą kontaktów, brak FK, `contact_id` logiczny). Reszta schematu to konfiguracja/referencja albo tabele mutowalne.
- **Luka retencji/RODO (dowód na żywej bazie):** `RetentionPurgeServiceImpl.purgeContactInteractions` woła `detachContactReferences` = tylko `contact_id := NULL`, NIE usuwa wiadomości. W demo 18/18 maili sprzed cutoffu purge (2026-05-13) ma `contact_id IS NULL` i pełne body. Dodatkowo `anonymize_customer()` szuka maili przez `contact_id IN (contact ...)`, więc po detach erasure Art. 17 ich już nie znajdzie. Nie ruszają też `campaign_contact*`, `scheduled_callback`, `contact_transcription`.
- **Partycjonowanie czasowe email/social koliduje z unikalnością biznesową** (zmierzone na scratch): `UNIQUE (tenant_id, message_id_header)` / `(tenant_id, external_message_id)` i PK `(message_id)` -> ERROR "must include all partitioning columns". Trzeba wariantu z kolumną czasową w kluczu (received_at/sent_at deterministyczne z IMAP/platformy) albo osobnej tabeli dedup. JPA: `em.find/em.merge` po samym `message_id` -> `@IdClass`.
- **`campaign_contact_archive`: obecny stan wystarcza** (Could). Pomiar 1.2M wierszy: DELETE 400k + VACUUM = ok. 1.6 s i ok. 129 MB WAL, rozmiar bez zmian (623 MB); DROP 4 partycji = 28 ms i 0.35 MB WAL, rozmiar 639->426 MB. Purge per-tenant kosztuje tyle samo w obu wariantach. `ON CONFLICT (record_id, campaign_id)` z archive function przestaje działać po dodaniu `archived_at` do PK. Po V091 indeksy `idx_cca_archived_at` i `idx_cca_campaign` nie mają czytelnika (grep Java + pg_proc + pg_views).
- **Martwe harmonogramy (pg_cron wyłączony, brak wywołań w Javie):** `archive_completed_campaign_contacts()` (30/30 kampanii kwalifikuje się, archiwum = 0 wierszy), `cleanup_expired_refresh_tokens` (refresh_token: 1331/1333 wygasłych; `RefreshTokenRepository.deleteExpiredAndRevoked` bez callera), `rotate_audit_log_partitions`/`drop_old_audit_log_partitions` i `rotate_plugin_invocation_log_partitions` (24 mies. backstop nieegzekwowany; `PartitionReclaimJob` obsługuje tylko 4 tabele contact*). Najtańsze dołożenie do maszynerii: `audit_log` + `plugin_invocation_log` do `PartitionReclaimJob` ze stałym horyzontem platformowym.
- **`campaign_contact` = dekoracyjne LIST(campaign_id) z jedyną partycją `campaign_contact_default`** (żaden kod aplikacji nie robi `PARTITION OF`; dokumentacja 06-database.md błędnie twierdzi że robi). Zmierzone: `CREATE TABLE ... PARTITION OF` przy istniejącym DEFAULT bierze AccessExclusiveLock na rodzicu i na default. Alternatywa zweryfikowana: HASH(campaign_id) działa z obecnym PK i UNIQUE(campaign_id, phone), pruning OK. Tabela nie ma RLS (PII: phone/imię/email), archiwum też nie.
- Duplikaty indeksów poza `contact`: `scheduled_callback` (`idx_callback_ready` == `idx_scheduled_callback_due`), `agent_group_member` (`idx_agent_group_member_lookup` == `idx_campaign_agent_member_lookup`).
- Antykandydaci: `agent_break` (UPDATE start_time = mutowalny klucz, UPDATE po samym id, 134 B/wiersz), `scheduled_callback` (`em.find` po id, mutowalne `scheduled_at`, 12 indeksów), `refresh_token` (UNIQUE token_hash), logi (`retention_purge_log`, `cron_log`) i cała konfiguracja/referencja.

**Why:** propozycja dla właściciela produktu; wdrożenie NIE zlecone. **How to apply:** przy kolejnym zadaniu partycjonującym lub ticketach retencji sprawdź czy luki wyżej zostały domknięte (grep callerów, `flyway_schema_history`). Otwarte pytania do PO: retencja treści wiadomości (osobna kategoria czy CONTACT_INTERACTIONS), horyzont audit_log/plugin_invocation_log, retencja `scheduled_callback`.
